# Employee Assistant travel workflow

The existing Employee Assistant now supports travel planning and approval submission inside its compact chat layout. The existing trip forms, flight/hotel portals, manager approvals and agency/travel-desk screens remain available.

## Delivery status

| Phase | Status |
| --- | --- |
| Conversation and intent detection | Implemented with local parsing and editable structured details |
| Flight and hotel discovery | Implemented using existing server-side SerpApi providers and validators |
| Selection and itinerary summary | Implemented; prices remain indicative |
| Request creation and manager approval | Implemented using the existing `createTrip`/`submitTrip` chain |
| Traditional travel-desk handoff | Implemented after approval and separate employee consent |
| Transactional provider integration | **Not implemented: no approved flight or hotel provider account was identified** |
| Booking tracking | Existing GENIQ records are displayed; independent provider verification is unavailable |

This is not a completed ticket-issuance or hotel-reservation integration. No new provider booking reference, ticket number, charge, or reservation is generated by the assistant. Existing legacy booking paths are unchanged and do not establish verified transactional provider access.

## Employee workflow

1. Select **Travel Assistance**, or describe a trip in chat.
2. Provide missing destination/dates and review the structured travel details. The origin comes from the authenticated employee's home city where available.
3. For a find/search request, discovery runs once essential details are present. Search buttons also work explicitly. Search failures are shown without substituting fake offers.
4. Select the flight legs and hotel/rate. Round trips and multi-city searches follow server-held continuation tokens. Morning/afternoon/evening and budgets filter comparison results.
5. Supply purpose, country and cost allocation details required by the existing travel-request validator. Review the estimated total, known cancellation conditions, policy exceptions and approval route.
6. Choose **Review trip summary**, then explicitly confirm submission. The assistant creates one request in the existing manager approval chain. It cannot approve the request.
7. After manager approval, refresh the status. With separate consent, **Send options to Travel Desk** creates existing agency service requests. Their status is shown in the assistant; requests are not bookings.
8. Open the trip/itinerary to review selected options or use the traditional service screens. Confirmed external reservations require a separately configured booking provider and final-price authorization.

The parser handles known airport/city aliases, ISO dates, named day/month dates, weekday references, durations, basic passenger/room counts, cabin, budgets and cancellation preferences. It is deliberately bounded, not an unrestricted LLM action executor. Ambiguous or unsupported details must be reviewed in the structured form. Multi-city legs and child ages are editable in search preferences. The assistant does not claim to understand every natural-language phrasing.

## Security and correctness

- Reuses `/api/employee-assistant/chat`; no parallel unauthenticated travel API.
- Only an explicit allowlist of tools can run. Model/user-supplied employee IDs, prices, booking statuses and provider tokens cannot override server-held records.
- Identity, department, company code and approval ownership are obtained from the authenticated employee record.
- Existing JSON body limits, authentication, origin checks, assistant throttling and SerpApi throttling apply.
- Structured plans are bound to employee, sign-in session and conversation. Submitted plans can be reattached for status/handoff after short chat-context expiry within the same sign-in session.
- Plan revisions invalidate old review confirmations. HMAC confirmations bind the exact server-side plan and action. Submission and travel-desk consent use distinct signatures.
- Expired quotes cannot be selected/submitted. Changing search criteria clears affected selections. Changing accounting details preserves the quoted selections but invalidates review consent.
- Trip creation, approval submission and plan linkage share one SQLite transaction. Durable plan linkage and a matching route/date check prevent duplicate trip requests.
- Travel-desk handoff uses one transaction and a plan ID on service details to prevent duplicate agency requests.
- Selected options appear on the authorized trip detail and itinerary pages; only sanitized views leave the server. Search continuation tokens and the SerpApi key stay server-side.
- Employee identity, accounting information, company policy and private records are not sent to Gemini. Travel searches send the necessary validated route/date/location parameters to SerpApi.
- New structured-tool actions are audited. The assistant does not log raw messages, secrets or payment details.
- Actual booking/cancellation tools return an explicit unavailable response. They cannot charge or manufacture confirmations.

Google Hotels does not expose a room-count search parameter. Room count is retained as a preference for desk verification; displayed totals are not a guaranteed combined multi-room price. Missing tax, baggage, fees, cancellation terms and prices remain visibly unknown rather than being invented.

## Transactional integration prerequisite

To implement actual flights and hotels, GENIQ must identify its approved provider(s), sandbox/production access and secure payment flow. SerpApi continuation/booking tokens are discovery tokens; they are not interchangeable with a transactional provider's offer IDs.

The remaining provider-specific work includes repricing matched offers, collecting validated passenger/guest details with consent, final payable total and fee disclosure, approval rechecks, provider-supported idempotency/reconciliation, secure hosted payment, signed webhook verification, order retrieval and provider-specific change/cancellation/refund handling. A verified provider order/reservation response must precede any new confirmed booking record.

Server configuration remains in `.env.local`; `.env.example` documents that the SerpApi key only enables discovery. No speculative provider flag or credential name was added that could imply real booking is enabled.

## Primary provider references reviewed

- [SerpApi Google Flights](https://serpapi.com/google-flights-api): flight discovery and selection/booking-option tokens.
- [SerpApi Google Hotels](https://serpapi.com/google-hotels-api): hotel discovery parameters and property details.
- [Duffel account/dashboard documentation](https://duffel.com/docs/guides/getting-started-with-the-dashboard): separate offers, orders, payments and booking lifecycle. GENIQ's commercial access was not established.
